# Database migration

Name: $ARGUMENTS. Use PascalCase that says what changes, e.g. `CreateRestaurants` or `AddNoteToReservations`.

1. **Is the database ready?** Run `docker compose ps` from the repo root.
   - Migrations are generated by comparing the entities with the dev database.
   - So the database must be running, and fully migrated: `npm run migration:show` shows no `[ ]` lines.
2. **Generate**, in `backend/`: `npm run migration:generate -- src/db/migrations/<Name>`.
3. **Read the generated file and check it:**
   - Only the expected tables and columns change.
     - **No unexpected `DROP`.**
     - A renamed property turns into drop + add, which loses data. Write that part by hand instead.
   - `uuid` primary keys have a default (`uuid_generate_v4()` or `gen_random_uuid()`), and moments are `timestamptz`.
   - Every `@Check` is there, e.g.:
     - the list of statuses;
     - `"startsAt" < "endsAt"`;
     - `"minCapacity" >= 1 AND "minCapacity" <= "capacity"`;
     - rating between 1 and 5.
   - Unique constraints and indexes from the entity are there (slugs, emails, `restaurantId + startsAt`).
   - Foreign keys have the intended `ON DELETE`: `CASCADE`, `RESTRICT` or `SET NULL`.
   - Exclusion constraints:
     - `CREATE EXTENSION IF NOT EXISTS btree_gist;` comes **before** `EXCLUDE USING gist (...)`. If TypeORM didn't add it, add it at the top of `up()`.
     - The `WHERE` lists only the active statuses.
   - `down()` undoes everything in the opposite order: constraints before tables. It doesn't drop the extension.
4. **Explain the SQL** to the user in plain words: which tables, columns and rules it creates, and why.
5. **Run:** `npm run migration:run`, then `npm run migration:show`. Every line must be `[X]`.
6. **Prove that `down()` works**, on the test database, which is safe to empty:
   ```bash
   DB_NAME=dine_yerevan_test npm run migration:run
   DB_NAME=dine_yerevan_test npm run migration:revert
   DB_NAME=dine_yerevan_test npm run migration:run
   ```
7. **Tests:** run `npm test`. The test helpers run every migration on the test database.
8. **Remind the user:** once this file is committed, it is never edited again. Later changes need a new migration.
